The Hardest Part of Building an AI News Reader Wasn’t the AI
Summarizing one article is easy. Deciding when six links are the same story is not.


The first version of Trace summarized articles one by one.

It worked, technically. It was also useless on a busy news day.

A company would announce a new product and the feed would fill with the original post, three rewrites, a Hacker News submission, a discussion about the submission, and a GitHub repository built around the announcement.

The system confidently summarized every link.

Six clean summaries. One actual story.

That was the moment I understood that summarization was not the hard part of building an AI news reader. The hard part was deciding what counted as new information.


A summary pipeline does not understand the feed


Article summarization is a contained task.

Give a model a title, URL, and extracted text. Ask for the central claim, important facts, and a readable explanation. Validate the result. Cache it so the same source is not processed again unnecessarily.

There are plenty of ways to get this wrong, but the boundaries are clear. One input becomes one output.

A feed has a different problem.

Its quality depends on relationships between items:

• Is this link a new story or another report about an existing one?
• Does the Hacker News thread add something that the original article does not?
• Is a GitHub repository part of the story, or merely related to the same broad topic?
• Has a developing event changed enough to deserve another place in tomorrow’s edition?
• If two links are duplicates, which one should survive?

An excellent summary model can answer none of those questions while looking at one article in isolation.

The feed needs a model of the collection, not just a model of each document.


The boring baseline was surprisingly useful


The first useful deduplication pass did not require an LLM.

It normalized titles, removed common words, ignored broad topic words, and compared the meaningful tokens that remained.

A simplified version looks like this:

function storyTokens(title: string): Set<string> {
  return new Set(
    title
      .toLowerCase()
      .replace(/[^a-z0-9\s]/g, " ")
      .split(/\s+/)
      .filter(token =>
        token.length >= 4 &&
        !STOPWORDS.has(token) &&
        !BROAD_TOPIC_WORDS.has(token)
      )
  );
}

function looksLikeSameStory(a: string, b: string): boolean {
  const left = storyTokens(a);
  const right = storyTokens(b);
  const shared = [...left].filter(token => right.has(token)).length;

  if (shared < 2) return false;

  const overlap = shared / Math.min(left.size, right.size);
  return overlap >= 0.5;
}

This catches more than I expected.

Publishers often preserve the same company name, product name, and action even when they rewrite the headline. “Acme launches a coding agent for teams” and “Acme’s new agent wants to automate team development” share enough specific language to deserve a closer look.

The baseline is fast, deterministic, cheap, and easy to debug.

It also fails in several interesting ways.


Failure one: the same event can use completely different words


Imagine these headlines:

OpenAI acquires ExampleCo in an all-stock deal

and:

Sam Altman’s latest purchase brings 40 engineers into the company

A person can connect them immediately if they know ExampleCo is the purchase being discussed. Token overlap may see two unrelated titles.

Entities help. Article text helps. Publication time helps. Links between pages help. None of those signals is sufficient alone.

This is where semantic similarity becomes useful, but it must be used carefully. Two articles can be semantically close because they discuss the same industry, not because they report the same event.

“Apple is struggling with AI” is a topic.

“Apple acquired Company X on Tuesday” is an event.

Collapsing a whole topic into one card is not deduplication. It is information loss.


Failure two: similar words can hide different stories


Broad technology terms produce false matches constantly.

Words such as “model,” “agent,” “startup,” “funding,” and “launch” appear everywhere. Even “OpenAI model” is not specific enough during a week with multiple releases, benchmarks, policy stories, and product updates.

This is why the implementation removes broad topic words before measuring overlap. A pair of titles should share the details that identify an event, not merely the vocabulary of the industry.

Numbers can be particularly valuable. A model version, funding amount, benchmark score, or release date may distinguish two otherwise similar stories.

They can also be traps. Every publication may round a number differently, and a developing story can change as new facts arrive.

There is no perfect threshold. A strict system leaves duplicates. A loose system merges stories that should remain separate.

The right choice depends on what is more damaging in the product.

For Trace, a duplicate is annoying. A false merge can hide a meaningful update. That makes precision more important than making the feed look perfectly tidy.


Failure three: a discussion is not just another copy


Hacker News created a useful complication.

A submission may link to the same article already present in Top Reads. At the URL level, it looks redundant. At the reader level, it may be the most valuable part of the story.

The source article explains what happened. The discussion may reveal whether the release works, what experienced developers distrust, which older project solved a similar problem, and where the announcement is misleading.

The same is true of a GitHub repository. A repo can be direct evidence that an idea is usable, a prototype built in response to a news event, or a completely separate tool that happens to share the same terms.

This changed the question from:

Are these items duplicates?

to:

What distinct job does each source perform for the reader?

Sometimes the correct interface is one storyline with several doors:

• Read the original announcement.
• See independent coverage.
• Join the Hacker News discussion.
• Open the repository.

Grouping does not have to mean deleting.


Failure four: stories change over time


Deduplication within one feed is easier than deduplication across days.

Yesterday, a security incident was reported. Today, the company confirmed the cause. Tomorrow, a patch may ship.

The subject is the same. The information is not.

If the system treats the title as the story, it will either repeat the incident every day or suppress the update because it looks familiar.

A better mental model is a storyline with state.

The storyline has an identity, sources, timestamps, and material developments. A new item should return to the feed only if it changes what a reader would believe or do.

That standard is harder to encode than title similarity, but it is closer to the product people actually want.

They do not care whether the URL is new. They care whether the knowledge is new.


Where AI helps, and where it does not


LLMs are useful after deterministic signals have narrowed the problem.

They can compare two borderline items and explain whether they describe the same event. They can identify the new fact in a follow-up. They can produce one clear summary from several sources while preserving links to the originals.

I do not want a model making every decision.

Calling an LLM for every pair of articles becomes expensive as the pool grows. More importantly, a model-only pipeline is difficult to reason about when it silently merges the wrong stories.

The practical system is layered:

1. Normalize URLs and remove exact duplicates.
2. Use title and entity signals for obvious matches.
3. Separate broad topics from specific events.
4. Send only ambiguous candidates for semantic comparison.
5. Keep source links and make grouping reversible.
6. Cache the result so repeated work does not become repeated cost.

The AI handles ambiguity. Deterministic code handles everything that does not need ambiguity.

That division is less exciting than “an agent reads the entire internet.” It is also easier to operate.


The final test is not technical


I can measure similarity scores, inspect clusters, and count duplicate URLs. None of those metrics proves the feed is good.

The real test is simpler:

When someone opens the briefing, do they encounter each important development once, with enough context to decide whether to go deeper?

If the answer is no, better prose will not save it.

Building Trace has made me much less impressed by systems that summarize a large number of links. Compression is useful, but compression without editorial structure only produces a denser form of overload.

Trace (https://www.yourtrace.online) is where I am testing these ideas in public. It combines top reads, community discussions, projects, and personalized briefings while trying to treat repeated coverage as one evolving story.

The summaries are visible.

The harder work is everything required before a story earns a place in the feed.
